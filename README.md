# Pickup Reserve

[![CI](https://github.com/zyounky/pickup-reserve/actions/workflows/ci.yml/badge.svg)](https://github.com/zyounky/pickup-reserve/actions/workflows/ci.yml)

Пет-проект [@zyounky](https://github.com/zyounky) для портфолио Go-разработчика.

На полке осталось 10 пачек молока. В одно и то же время 100 покупателей добавляют по одной в заказ на самовывоз. Кому можно пообещать товар? Pickup Reserve отвечает на этот вопрос до оплаты заказа. Сервис на Go резервирует всю корзину в выбранном магазине, возвращает товары в продажу по истечении срока брони и списывает остаток при выдаче.

## Воспроизвести гонку покупателей

Понадобится Go 1.23 или новее. Все команды выполняются из корня репозитория. В первом терминале запустите API:

```sh
go run ./cmd/server
```

Во втором терминале запустите покупателей:

```sh
go run ./cmd/rush -buyers 100 -units 10
```

```text
buyers=100 units=10 created=10 insufficient_stock=90 available=0
```

Каждый запуск создаёт отдельный демонстрационный магазин, регистрирует поставку и отправляет HTTP-запросы с разными ключами. Затем клиент читает остаток через API и сверяет его с числом успешных броней. При расхождении команда завершается с ошибкой. Для проверки последней единицы укажите `-units 1`.

## Как ведёт себя бронь

| Событие | Состояние | Что меняется в магазине |
| --- | --- | --- |
| Товара хватает по всем позициям | `active` | Позиции недоступны другим покупателям |
| Заказ выдан | `confirmed` | Зарезервированные единицы списаны с физического остатка |
| Покупатель отменил заказ | `cancelled` | Единицы снова доступны |
| Наступил срок окончания | `expired` | Единицы доступны уже при следующем запросе |

В каждый момент `available = on_hand − reserved`. Если хотя бы одной позиции не хватает, вся корзина получает HTTP 409. Подтверждение или отмену можно повторить. Попытка подтвердить отменённую или просроченную бронь вернёт 409.

### Повтор после сетевого сбоя

При создании клиент передаёт `Idempotency-Key`. Если ответ потерялся, тот же ключ с теми же магазином, позициями и сроком вернёт прежний ID и текущее состояние. Порядок позиций значения не имеет. Первая успешная попытка получает `201 Created`, повторная — `200 OK` и `Idempotency-Replayed: true`. Изменение корзины с уже использованным ключом вернёт 409. Приёмка товара прибавляет указанное количество при каждом вызове.

## Попробовать API вручную

Пример для Bash и curl. Сначала зарегистрируйте поставку, затем зарезервируйте две единицы на пять минут:

```sh
base=http://127.0.0.1:8080
curl -sS -X POST "$base/v1/stores/msk-01/inventory/milk/receipts" \
  -H 'Content-Type: application/json' -d '{"quantity":5}'

curl -i -X POST "$base/v1/reservations" \
  -H 'Content-Type: application/json' -H 'Idempotency-Key: order-184' \
  -d '{"store_id":"msk-01","items":[{"sku":"milk","quantity":2}],"ttl_seconds":300}'

curl -sS "$base/v1/stores/msk-01/inventory/milk"
```

После первого запуска на пустом хранилище последний запрос вернёт:

```json
{"store_id":"msk-01","sku":"milk","on_hand":5,"reserved":2,"available":3}
```

Путь к созданной брони есть в заголовке `Location`. В примерах ниже `{id}` обозначает идентификатор из ответа.

| Метод и путь | Назначение |
| --- | --- |
| `GET /healthz` | Проверить, что процесс отвечает |
| `POST /v1/stores/{storeID}/inventory/{sku}/receipts` | Принять поставку |
| `GET /v1/stores/{storeID}/inventory/{sku}` | Узнать физический, зарезервированный и доступный остатки |
| `POST /v1/reservations` | Создать бронь на 1–100 разных SKU |
| `GET /v1/reservations/{id}` | Проверить состояние и время истечения |
| `POST /v1/reservations/{id}/confirm` | Зафиксировать выдачу |
| `POST /v1/reservations/{id}/cancel` | Отменить бронь |

`ttl_seconds` по умолчанию равен 300. Допустимы значения от 1 до 86400. Для приёмки и создания брони нужен `Content-Type: application/json`. При нехватке товара код в `error.code` равен `insufficient_stock`.

## Реализация и границы

- [internal/stock](internal/stock) владеет остатками. Проверка всей корзины и запись брони проходят под одной блокировкой. Другой запрос увидит либо исходное состояние, либо полностью созданную бронь.
- По умолчанию сервис сохраняет состояние в `data/stock.json`. Перед ответом об успешной записи он записывает временный файл, вызывает `Sync`, закрывает файл и переименовывает его. При ошибке сохранения изменения в памяти откатывать не требуется — новое состояние ещё не опубликовано. Ключи повторов восстанавливаются из снимка при запуске.
- Истечение вычисляется по `expires_at` при обращении к сервису. В тестах время задаётся явно, поэтому можно проверить запрос ровно в момент истечения.
- [internal/httpapi](internal/httpapi) преобразует JSON в операции над остатками, а доменные ошибки — в HTTP-ответы. Сервер, HTTP-клиент и тесты используют стандартную библиотеку Go.

Снимок рассчитан на один процесс и одного владельца файла. Стоимость записи растёт вместе со всей историей, а подсчёт резервов просматривает сохранённые брони. Для нескольких реплик потребуется общее транзакционное хранилище. API запускается на loopback; операции магазина открыты для локальной демонстрации.

## Сборка и проверки

```sh
go test ./...
go test -race ./...
go vet ./...
```

GitHub Actions также собирает контейнер и прогоняет `cmd/rush` через опубликованный HTTP-порт. Локальный запуск через Docker с именованным томом:

```sh
docker build -t pickup-reserve .
docker run --rm -p 127.0.0.1:8080:8080 -v pickup-data:/data pickup-reserve
```
